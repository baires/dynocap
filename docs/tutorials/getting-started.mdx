# Getting Started with MicroVM

Build the signed CLI on an Apple Silicon Mac, boot one sealed Linux guest, and run a command inside it.

You will:

1. Verify system prerequisites on Apple Silicon.
2. Build the signed CLI binary.
3. Check and repair your setup with `microvm doctor --fix`.
4. Launch a raw sandbox and execute commands over vsock.
5. Safely destroy the sandbox.

---

## Prerequisites

MicroVM requires:

- **Hardware:** Apple Silicon Mac (M1/M2/M3/M4).
- **Operating System:** macOS 13 (Ventura) or newer.
- **Developer Tools:**
  - Xcode Command Line Tools (`xcode-select --install`, Swift 5.9+)
  - Go 1.22+ (`brew install go`)
  - Node.js 22+ (`brew install node`)
  - `mke2fs` from e2fsprogs (`brew install e2fsprogs`)

Verify that the tools are present in your shell:

```sh
swift --version
go version
node --version
mke2fs -V
```

---

## Step 1: Install Dependencies and Build the Release CLI

MicroVM uses Apple's `Virtualization.framework`, which requires the `com.apple.security.virtualization` entitlement. The build script compiles the Swift CLI in release mode, compiles the companion Go binaries, and applies the code signature.

From the root of your `microvm` repository:

```sh
# Install repository development tooling
npm ci

# Build the release CLI and sign it with the virtualization entitlement
./scripts/build-macos.sh
```

Add the built binary to your `PATH` for the current terminal session:

```sh
export PATH="$PWD/.build/release:$PATH"
which microvm
```

> **Note:** If you rebuild `microvm` at any point, re-run `./scripts/build-macos.sh` to ensure the binary is properly code-signed.

## Step 2: Check Your Setup

Go to your project and run `microvm doctor`. It checks the platform, code signing, companion binaries, guest image, runtime, and daemon, and changes nothing:

```sh
cd ~/code/my-app
microvm doctor
```

Doctor reads your project's files to pick its runtime, the same way `clone` does:

| File at the project root                                               | Runtime       |
| :--------------------------------------------------------------------- | :------------ |
| `package.json`                                                         | `node:24`     |
| `pyproject.toml`, `uv.lock`, `requirements.txt`, `setup.py`, `Pipfile` | `python:3.14` |
| `go.mod`                                                               | `go:1.27`     |

On a fresh install, the guest image and runtime are not built yet. Each failure says what is wrong and what to run:

```text
ERROR   images             The guest image for aarch64 has not been built yet.
                           Next: Run microvm doctor --fix to build the guest image (downloads pinned Alpine files; needs Go).
ERROR   runtime            Runtime python:3.14 is not prepared for aarch64 yet. This project's pyproject.toml needs it.
                           Next: Run microvm doctor --fix to prepare python:3.14 (downloads verified inputs; takes a few minutes).

2 required checks failed. Run microvm doctor --fix to repair them.
```

To prepare a different runtime, pass `--runtime`, for example `microvm doctor --fix --runtime node:22`. Run outside a project, doctor requires no runtime. It lists the prepared ones instead, because raw sandboxes need none.

---

## Step 3: Repair It with `doctor --fix`

```sh
microvm doctor --fix
```

`--fix` builds the guest image, prepares your project's runtime, and restarts a daemon left over from an older build. Every download is pinned and verified. It then runs the checks again and ends with `Required checks passed.`

Doctor finds the microvm checkout from the `microvm` binary, so you can run it in any directory. You can also name the project instead of changing directory: `microvm doctor --fix ~/code/my-app`.

> **Tip:** After you rebuild `microvm`, run `microvm doctor --fix` again. It restarts the daemon so it runs the new build.

## Step 4: Boot a Raw Sandbox

A raw sandbox boots the minimal Alpine Linux image without importing a project workspace.

Start a sandbox named `my-first-box`:

```sh
microvm run --name my-first-box
```

Output:

```text
running my-first-box
```

Behind the scenes:

1. The `microvm` CLI launched the per-user background daemon (`~/.microvm/daemon.sock`).
2. The daemon booted a Linux virtual machine with 1 vCPU and 1024 MB RAM via Virtualization.framework.
3. The guest booted its initramfs in under 200ms and launched the internal Go `microvm-agent`.
4. The agent connected back over `virtio-vsock` (guest port 5252).

Verify the sandbox status:

```sh
microvm ps
```

You will see:

```text
NAME/ID       KIND     PHASE    RUNTIME  NETWORK  TTL    RETENTION
my-first-box  sandbox  running  minimal  none     29m    -
```

Notice that `NETWORK` is `none`. The sandbox is completely offline. No network interface exists inside the guest.

---

## Step 5: Execute Commands Inside the Sandbox

Run commands inside your guest with `microvm exec`:

```sh
microvm exec my-first-box -- uname -a
```

Output:

```text
Linux microvm 6.18.62-0-virt #1-Alpine SMP PREEMPT_DYNAMIC aarch64 Linux
```

Test running an isolated shell command:

```sh
microvm exec my-first-box -- sh -c "echo 'Hello from MicroVM' && id"
```

Output:

```text
Hello from MicroVM
uid=0(root) gid=0(root) groups=0(root)
```

MicroVM streams stdout and stderr separately, and exits with the exact status code returned by the guest command.

---

## Step 6: Destroy the Sandbox

When your work is done, remove the sandbox:

```sh
microvm rm my-first-box --force
```

Output:

```text
removed my-first-box
```

Because `my-first-box` was actively running, `--force` explicitly confirms discarding running processes. The daemon terminates the virtual machine and cleans up runtime descriptors.
